# Reference stub сервиса команды

Учебный эталон контракта [`api/openapi.yaml`](../api/openapi.yaml): 8 операций,
`X-Api-Key`, in-memory состояние и детерминированный сид. Это не продакшен —
stub нужен, чтобы команда могла сверить свой сервис с контрактом и прогнать
`check-service` до сдачи.

## Запуск

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -e ".[dev]"

# TEAM_API_KEY по умолчанию test-key; для локальной проверки менять не нужно
uvicorn stub.app:app --host 127.0.0.1 --port 8080

curl -s http://127.0.0.1:8080/healthz
# {"status":"ok","service":"team-service","version":"2.4.0","time":"..."}
```

Ключ задаётся переменной окружения `TEAM_API_KEY` (по умолчанию `test-key`).
`/healthz` — единственная операция без ключа; остальные без `X-Api-Key` или с
неверным ключом отвечают `401` в конверте `{code, message, details?}`.

Состояние живёт в памяти процесса: перезапуск возвращает сид. Это осознанно —
stub не БД и не должен «накапливать» данные между прогонами.

## Redis-кэш (опционально)

Stub может кэшировать read-ответы в Redis. Кэш **выключен по умолчанию**: без
`REDIS_URL` приложение ведёт себя как раньше.

```bash
# Запуск Redis локально
docker run --rm -p 6379:6379 redis:7-alpine

# Запуск stub с кэшем
REDIS_URL=redis://localhost:6379/0 REDIS_TTL=60 \
  uvicorn stub.app:app --host 127.0.0.1 --port 8080
```

Переменные окружения:

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `REDIS_URL` | пусто | URL Redis, например `redis://localhost:6379/0`; пусто — кэш выключен |
| `REDIS_TTL` | `60` | TTL кэша в секундах |

Кэшируются read-операции: `GET /v1/requests`, `GET /v1/requests/{id}/quotes`,
`GET /v1/orders/{id}`, `GET /v1/points`. При `POST /v1/requests` и
`POST /v1/requests/{id}/quotes` связанные ключи инвалидируются. Если Redis
недоступен, stub продолжает работать на in-memory состоянии.

## Сидовые данные

| Что                               | ID         | Значения                                                                                                                        |
| --------------------------------- | ---------- | ------------------------------------------------------------------------------------------------------------------------------- |
| Заявка (open, без котировки)      | `req_5001` | Москва → Владивосток, 18.5 т, дедлайн ≈ +2 дня, 100 баллов                                                                      |
| Заявка (quoted)                   | `req_5002` | СПб → Новосибирск, 12 т, дедлайн ≈ +1 день, 80 баллов                                                                           |
| Котировка (набор из 1)            | `quo_7007` | по `req_5002`, `variant` `balanced`, `price_rub` 760000, срок 90 ч, `rail:saint-petersburg-novosibirsk`, `valid_until` ≈ +4 дня |
| Заказ (delivered)                 | `ord_6003` | по `req_5002`, `price_rub` 760000, создан ≈ −1 день, `delivered_at` ≈ −2 часа                                                   |
| Начисление `order_delivery`       | `pts_9001` | `ord_6003`, 80 баллов, ≈ −2 часа                                                                                                |
| Начисление `subcontract_delivery` | `pts_9002` | `sub_9001`, 40 баллов, ≈ −1 час                                                                                                 |

ID взяты из [`api/mocks`](../api/mocks), но набор маленький: для conformance
этого достаточно. `ord_6003` — заказ для `--order-id` по умолчанию в CI.
Времена в сиде считаются от `utc_now()` при старте приложения, поэтому
`response_deadline`/`valid_until` не протухают: `req_5001` остаётся доступной
для живой публикации набора котировок в любой день.

## Поведение операций

| Операция                        | Успех                      | Ошибки и идемпотентность                                                                                                                                                                                                                                                                                                                                                                        |
| ------------------------------- | -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /healthz`                  | `200` `Health`             | без ключа; `503` в контракте — заглушка не отдаёт                                                                                                                                                                                                                                                                                                                                               |
| `GET /v1/requests`              | `200` массив `Request`     | `401`                                                                                                                                                                                                                                                                                                                                                                                           |
| `POST /v1/requests`             | `201` `Request`            | повтор с тем же `Idempotency-Key` и телом — `200`; другое тело или уже занятый `request_id` — `409 request_conflict`; нет заголовка — `400`; битый `Idempotency-Key` — `422`                                                                                                                                                                                                                    |
| `GET /v1/requests/{id}/quotes`  | `200` массив `Quote`       | неизвестная заявка — `404`                                                                                                                                                                                                                                                                                                                                                                      |
| `POST /v1/requests/{id}/quotes` | `201` `QuoteBatch`         | один активный набор из 1–3 вариантов: `variant` и `quote_id` уникальны в наборе, `valid_until` каждого ≥ `response_deadline + 60 s`; повтор публикации — `409 quote_exists` (в контракте у операции нет `200`); после дедлайна — `409 request_closed`; неизвестная заявка — `404`; 4 варианта, повтор `variant`/`quote_id` — `422`                                                              |
| `GET /v1/orders/{id}`           | `200` `OrderSnapshot`      | неизвестный/чужой заказ — `404`; снимок read-only                                                                                                                                                                                                                                                                                                                                               |
| `POST /v1/orders/{id}/notify`   | `204` без тела             | доставка: повтор по `(order_id, subcontract_id)` — `204`, другое тело — `409 notification_conflict`, неизвестный заказ — `404`; `order_won`/`order_lost`: обязателен `Idempotency-Key` (без него — `400`), повтор с тем же ключом и телом — `204`, другое тело — `409`, неизвестный `event`/`reason` или `order_id` не из пути — `422`; заказ для `order_won`/`order_lost` знать не обязательно |
| `GET /v1/points`                | `200` массив `PointsEntry` | только свои начисления; ручки записи нет                                                                                                                                                                                                                                                                                                                                                        |

`notify` фиксирует событие, но **не меняет** статус заказа, `delivered_at` и
баллы: доставкой владеет система, у команды нет таких операций. `GET /v1/points`
возвращает только сид: баллы начисляет системный settlement, а не stub.

Четыре тела `notify`: `delivered`, `subcontract_delivered` (события доставки,
без поля `event`) и `order_won`/`order_lost` (с `event`). Тип определяется
полем `event`; `order_lost` — экспериментальное событие, `reason` —
`not_selected | no_quote`. Идемпотентность событий — по заголовку
`Idempotency-Key` (`exchange:order:<id>:won:v1`,
`exchange:order:<id>:lost:<team_id>:v1`), доставки — по паре
`(order_id, subcontract_id)`.
